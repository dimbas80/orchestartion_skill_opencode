Инициализация нового проекта. Выполняется **до** любого интервью — шаблон и индекс должны существовать, пока мы выясняем требования. После шага 8 сразу начинается интервью: инициатива передачи — на тебе, не жди команды «запусти brainstorming».

## Шаги

1. **Корень проекта.** Если пользователь не назвал путь — спроси. Каталог не существует — создай (включая родителей).
2. **Защита от перезаписи.**
   - `.orchestration/orchestration.yml` есть → шаг 3 пропускать целиком (шаблон уже скопирован; не пересобирать и не перекатывать поверх). Но это ещё не «проект инициализирован»: полная инициализация = orchestration.yml + `.git` + `.codegraph/` + субагенты конвейера (шаг 6). Ситуация «часть есть, часть нет» — реальный кейс (шаблон скопировали в прошлой сессии, шаги 4–6 не добили): дополни только недостающие шаги 4–6 и продолжи к отчёту/передаче в brainstorming, не спрашивая разрешения и не перезапуская шаги 2–3. Всё на месте → предложи только `codegraph index`/`sync` и остановись.
   - Корень не пуст (кроме `.git`/`.gitignore`) → покажи содержимое и спроси, продолжать ли.
   - Корень пуст, НО рядом лежит предыдущее состояние проекта (summary.md с планом, `.scratch/`, `.superpowers/`, git-история ветки с отчётами `workflows/`) → проект не новый, а его артефакты частично потеряны (каталог чистили между сессиями). Сверься с этими следами ДО объявления проекта новым. Есть завершённая работа с артефактами, которых нет на диске, — не переинициализируй молча: спроси пользователя (восстановить vs с нуля).
3. **Шаблон — первым делом и целиком.** Шаблон лежит **внутри каталога этого скилла**: `<каталог_скилла>/template/`.
   Каталог скилла — там, где лежит этот SKILL.md (харнесс сообщает его при загрузке скилла);
   если путь неизвестен — найди: `find .agents/skills ~/.agents/skills ~/.zcode/skills ~/.config/opencode/skills -maxdepth 3 -type d -name project-init 2>/dev/null`.
   Скопируй целиком, включая dot-файлы (завершающий `/.` обязателен):

   ```bash
   cp -a <каталог_скилла>/template/. <корень>/
   ```

   Копируй **до любых проектных решений**. Запрещено:
   - собирать структуру по памяти или «под задачи проекта» (`firmware/`, `grafana/`, `homeassistant/`, `scripts/` и т.п. — вместо `src/`);
   - писать orchestration-файл вручную или в другом расширении (только `orchestration.yml` из шаблона);
   - удалять или переименовывать шаблонные каталоги (`src/`, `tests/`, `docs/`).
   Проектные каталоги создаются позже — по утверждённой архитектуре и мере необходимости
   (`lib/`, `include/`, `hardware/`, доменные папки). Кажется, что шаблон не подходит проекту? —
   Всё равно скопируй и отдельной строкой скажи пользователю, что именно не подошло.
   Не собирай структуру проекта по памяти — единый источник — этот каталог.
4. **Git.** Если `.git` нет — `git init`. Убедись, что `.gitignore` на месте (идёт из шаблона): в git не должны попадать `.orchestration/`, `.scratch/`, `docs/`, `workflows/`, `.codegraph*/`, `summary.md` — только сам проект (`src/`, `tests/`, `README.md` и каталоги, созданные по необходимости). Если инициализируешь существующий каталог с уже затреканными служебными файлами — `git rm --cached` их (файлы оставь на диске). Каталог вне владения текущего пользователя (смонтированный диск) даёт `dubious ownership` при первом `git status`: это настройка доверия, не ошибка инициализации — `git config --global --add safe.directory <путь>` и продолжай.
5. **CodeGraph.** В корне проекта выполни `codegraph init`. Если CLI недоступен — предупреди пользователя и продолжи (индекс можно построить позже: `codegraph index`).
6. **Субагенты конвейера.** Определи харнесс и поставь файлы ролей architect/coder/reviewer (установка: `install/zcode.md` / `install/opencode.md` набора; сборка — `install/emit.sh`):

   ```bash
   # zcode (проектный scope):
   <набор>/install/emit.sh zcode <корень>      # → .zcode/agents/{architect,coder,reviewer}.md
   # opencode (проектный scope):
   <набор>/install/emit.sh opencode <корень>   # → .opencode/agent/build.md + 3 субагента
   ```

   Если набор набора нет под рукой — скопируй тела ролей из `agents/` набора в agent-файлы харнесса вручную (frontmatter: `description` — строка `> …` тела роли; opencode — `mode: subagent`). Уже стоящие агент-файлы не перезаписывай молча: покажи diff и спроси. Скиллы (`cp -a skills/* .agents/skills/`) ставятся один раз на машину/репо — проверь их наличие (`ls .agents/skills | head`), не дублируй.
   Отсутствие субагентов конвейером не блокирует: соло-режим работает и без них — но скажи пользователю, что routed-путь (architect → coder → reviewer) пока недоступен.
7. **Отчёт.** Покажи дерево верхнего уровня и одну строку: что игнорируется git'ом.
   Шаблонный README («Engineering Project» / run by the leading agent session) —
   заглушка, не deliverable: как только утверждён design-doc или сделан первый
   запуск CLI, перепиши README под проект — что делает, как запускать, карта
   source-of-truth, внешние активы (kb в профиле, стабильные симлинки путей).
8. **Передача — немедленно в brainstorming.** Сразу после отчёта загрузи скилл
   `brainstorming` и начни интервью — это этап discovery конвейера,
   инициатива перехода на тебе. Если пользователь принёс готовый текст (IDEA.md, заметка
   Obsidian, черновой план) — это **вход интервью, а не замена ему**: прочитай источник,
   спрашивай по пробелам и внутренним противоречиям. Не пиши `requirements.md` сам, без
   интервью, — требования, составленные без вопросов, молча переносят противоречия
   источника в архитектуру. На выходе brainstorming: design doc в `docs/product/`,
   `GLOSSARY.md` + `docs/adr/` по ходу (домен-хук) и предложение стресс-теста через `grilling`.

## Почему так

- Шаблон несёт `orchestration.yml` (маршрутизация этапов по ролям, контракты хендоффов, лимиты реворка), адаптеры `docs/agents/` для скиллов планирования и заготовку `.gitignore`. Без них роли в отдельных сессиях не договорятся. Шаблон **единый** (software + embedded): architect — и софт-, и хард-архитектор, хард-материалы создаются только при необходимости.
- `.gitignore` из шаблона — до первого коммита: иначе `.orchestration/`, `docs/`, `workflows/` затрекаются и служебное утечёт в git (проверено на живом проекте).
- Субагенты ставятся на шаге инициализации, а не «когда понадобится диспатч»: первый же routed-диспатч находит файлы ролей на месте, и Model Gate читает их модели из agent-файлов, а не угадывает.
- «Готовый текст вместо интервью» — антипаттерн: источник несёт внутренние противоречия трёх классов (одно значение в одном месте и другое в другом; выбранная деталь или настройка vs реальное требование; допущение об окружении vs реальная цель развёртывания), и вылавливает их именно интервью, где пользователь сам даёт значения. Нерешённое — в decision-log и раздел «Риски открытые» requirements.
- Если оркестратор уже нагенерил файлы вручную до project-init (orchestration с другим расширением, доменные каталоги `firmware/`/`homeassistant/`/`scripts/`, requirements без интервью) — шаблон при re-align это перепишет/вычистит, а рукописные requirements/decision-log останутся на диске, но выпадут из git (`docs/` в `.gitignore`). Запускай project-init первым действием, до создания любых файлов.
- `git commit` после правки requirements.md/decision-log.md честно отвечает «nothing to commit» — это НЕ ошибка: `docs/` и `.orchestration/` намеренно не версионируются (в git — только `src/`, `tests/`, `README.md`). Не форс-трекай служебное обратно через `git add -f`.
- `codegraph init` до первого кода: индекс пустой — нормально, он наполняется по мере работы; важно, что `.codegraph/` в корне с первого дня и не коммитится.
- Пустой каталог ≠ новый проект: `summary.md`, `.scratch/`, ledger и git-история переживают очистку видимых файлов. Сверка с этими следами до инициализации ловит потерю артефактов — иначе шаблон молча затирает следы, а дальнейшие отчёты ссылаются на несуществующие файлы.

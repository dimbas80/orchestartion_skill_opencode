# Рецепты разбора пунктов ревью

Развёрнутые рецепты verbatim; ядро дисциплины — в SKILL.md.

## «Удалить дубликат» — сначала найти оставшийся экземпляр

Ревью часто формулирует «удалить дублирующий вызов/копию». Перед удалением подтвердите
grep-ом, что второй экземпляр **существует** и находится в нужном контексте, и что удаляемый
— не единственный путь вызова.

```
IF пункт ревью: «удалить дублирующий X»
  1. grep X → сколько вхождений и где (loop? прерывание? функция, вызываемая и из loop, и из while-циклов?)
  2. IF оставшийся путь единственный и именно он кормит функциональность
       → удалить дубликат в другом месте, а этот сохранить, и написать это в отчёте как отклонение
  3. IF дубликатов действительно два в сравнимом контексте → удалить указанный
```

Почему: удаление «дубликата», который на деле единственный, выключает функциональность и
при этом **не ломает сборку** — ошибка всплывёт только на железе или у пользователя.
Обратный признак: если удаляемый вызов находится в функции, которую вызывают ещё и из
`while`-циклов обработки, то «перенос в основной цикл» эквивалентен удалению для этих циклов.

## Числа в ревью — пересчитывать, а не копировать

Размеры в байтах, номера строк, «в 10 раз больше», единицы измерения в тексте ревью —
это утверждения автора, а не факт кода. Перед правкой пересчитай их по коду/данным
(байты UTF-8 против символов, мс против с, сдвиг строк предыдущим батчем).

```
IF число из ревью расходится с пересчётом
  → правку делай по пересчитанному значению
  → в отчёте отдельным пунктом: «в ревью указано X, фактически Y, потому что …»
```

Почему: неверная цифра в ревью обычно означает, что и вывод из неё неверен (например,
«обрезка команды» считалась по символам, а буфер измеряется в байтах). Если молча взять
цифру ревью, в код и в отчёт уедет ложное обоснование, а ревьювер сверит его с кодом.

## Пункт ревью уже закрыт — проверь, а не переделывай

Перед реализацией пункта проверь текущее состояние кода и историю предыдущих батчей:
замечание могло быть исправлено раньше (в т.ч. в рамках другого пункта).

```
IF код уже соответствует требованию
  → не вносить «эквивалентную» правку ради галочки
  → проверить, что требование выполнено с запасом, и внести недостающее обоснование
    (комментарий/тест/расчёт) в код и отчёт
  → в отчёте: «уже сделано в <батч>, проверено так-то»
```

Почему: повторная «правка» уже исправленного места — лишний риск регрессии и шум в диффе,
а молчание в отчёте читается как пропущенный пункт.
